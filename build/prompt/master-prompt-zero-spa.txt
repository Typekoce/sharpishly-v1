# 1. NON-NEGOTIABLE ARCHITECTURE RULES

## 1.1 Zero-dependency discipline

- Do not import, reference, link, or suggest any third-party JavaScript, CSS, fonts, icons, analytics, polyfills, or UI libraries.
- Do not use `<script src="https://...">`, `<link rel="stylesheet" href="https://...">`, `@import url("https://...")`, CDN URLs, npm package names, or external asset URLs.
- Do not require Node.js, a package manager, TypeScript compilation, JSX, a framework, or a build pipeline.
- All JavaScript must be authored as standards-based vanilla ES modules.
- All CSS must be authored natively.
- All icons, illustrations, diagrams, textures, and decorative artwork must be inline SVG, CSS-generated visuals, canvas-generated visuals, or procedural graphics.
- If photographic imagery is appropriate, support local user-supplied images through `<input type="file">`, drag-and-drop, and `URL.createObjectURL()`. Do not invent external image URLs.

## 1.2 File structure

Choose one of the following structures and state which one you selected:

### Option A — Single-file SPA

Use this when the application is compact enough to remain clear and maintainable.

```text
index.html
```

The file must contain:

- Semantic HTML
- Embedded `<style>` organized with CSS cascade layers
- Embedded `<script type="module">` organized into clearly labeled modules/sections
- Inline SVG artwork
- Complete CSS and JavaScript with no truncation

### Option B — Multi-file native ES-module SPA

Use this for a larger, more modular application.

```text
index.html
styles/
  main.css
  reset.css
  tokens.css
  base.css
  layout.css
  components.css
  utilities.css
  motion.css
js/
  main.js
  app.js
  state.js
  router.js
  render.js
  data.js
  theme.js
  interactions.js
  media.js
  accessibility.js
  utils.js
```

Requirements:

- `index.html` must use `<script type="module" src="./js/main.js">`.
- CSS must be loaded through native `<link rel="stylesheet">` elements or a single local CSS entry file that uses `@import` only for local files.
- Every file must begin with a concise header comment explaining its responsibility.
- No circular imports.
- No global mutable variables except an explicitly documented application namespace if unavoidable.
- Use relative paths so the project works from a local static server.

## 1.3 Modular separation

Separate concerns cleanly:

- **State:** Central application state, persistence, selectors, and update events.
- **Routing:** URL/path or hash routing, navigation events, deep links, scroll restoration.
- **Rendering:** DOM construction, view templates, lists, dialogs, drawers, and empty states.
- **Domain logic:** Theme-specific calculations, simulations, filters, scoring, validation, or transformations.
- **Media:** Canvas, SVG, audio, image handling, animation loops, and visual effects.
- **Accessibility:** Focus management, live-region announcements, keyboard shortcuts, and reduced-motion handling.
- **Utilities:** Formatting, IDs, sanitization, feature detection, storage wrappers, and event helpers.

Avoid monolithic “god files.” Each module should have a clear responsibility and a concise public API.

## 1.4 State management

Implement a centralized state store, for example `AppState`, using one of these patterns:

- A `Proxy`-based reactive store
- An `EventTarget`-based store
- A small pub/sub store with explicit `subscribe`, `getState`, and `dispatch` APIs

Requirements:

- State updates must be predictable and traceable.
- Do not mutate state indirectly from arbitrary DOM handlers.
- Persist only appropriate user preferences and user-created data in `localStorage`.
- Wrap all `localStorage` access in `try/catch` and handle quota, privacy-mode, serialization, and unavailable-storage failures gracefully.
- Synchronize meaningful application state with the URL using either:
  - Hash routing, or
  - History API / Navigation API path routing
- Deep links must restore the intended view, filters, selected item, or simulation parameters where sensible.
- Do not store secrets, large binary blobs, or unnecessary personal data.

## 1.5 Security and DOM hygiene

- Never place untrusted user input directly into `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, or inline event-handler attributes.
- Prefer `textContent`, `document.createElement()`, `append()`, `replaceChildren()`, and explicit attribute assignment.
- If HTML/SVG strings are genuinely necessary, use a narrowly scoped sanitization approach and, where available, integrate with `window.trustedTypes`.
- Escape or safely encode all user-provided values used in URLs, IDs, labels, `title` attributes, and custom data attributes.
- Do not execute user-supplied code.
- Do not use `eval()`, `new Function()`, or unsafe dynamic script injection.
- Validate file types and sizes before processing user uploads.
- Revoke object URLs with `URL.revokeObjectURL()` when they are no longer needed.

# 2. MODERN WEB PLATFORM SHOWCASE

Demonstrate real, working modern-platform capabilities. Use progressive enhancement: the application must remain usable if a feature is unsupported.

## 2.1 CSS architecture and theming

Use CSS Cascade Layers to organize styles:

```css
@layer reset, tokens, base, layout, components, utilities, motion;
```

Requirements:

- Define a semantic design-token system using custom properties.
- Use `oklch()` and/or `oklab()` for the core palette.
- Use `color-mix()` to derive hover, active, muted, border, surface, focus, and emphasis colors.
- Use relative color syntax where supported, with sensible fallbacks.
- If `contrast-color()` is used, provide a fallback color strategy because support may vary.
- Use native CSS nesting where it improves readability.
- Use `@scope` for at least one clearly bounded component or thematic module, with a fallback that does not depend on scoping for core usability.
- Use custom properties to drive theme variants, density, motion intensity, and light/dark preferences.

### Responsive design

- Design mobile-first from 320 px upward.
- Ensure zero horizontal overflow at common widths, including 320 px, 375 px, 768 px, 1024 px, 1440 px, and ultra-wide layouts.
- Use fluid typography and spacing with `clamp()`.
- Use modern viewport units such as `dvh`, `svh`, `lvh`, and `dvw` where appropriate.
- Use Container Queries:
  - `container-type: inline-size`
  - `cqi`, `cqw`, `cqh`, or related container units
  - Container size queries for card, panel, sidebar, and widget adaptation
- Use Container Style Queries where appropriate, for example changing a card’s presentation based on a custom property such as `--density`, `--mode`, or `--emphasis`.
- Use CSS Grid, including `subgrid` where useful, to align card headers, metadata, actions, and footers across components.

### Modern controls and overlays

Use native HTML controls before custom JavaScript controls:

- `<dialog>` for modal content where appropriate.
- `[popover]` and `popovertarget` for non-modal menus, tooltips, filters, command panels, or contextual help.
- `<details>` and `<summary>` where a disclosure is semantically appropriate.
- Native form controls with labels, descriptions, `required`, `pattern`, `inputmode`, `autocomplete`, and validation where relevant.
- `field-sizing: content` on suitable inputs or textareas, with a usable fallback.
- `:user-valid` and `:user-invalid` for progressive form feedback.
- `:focus-visible` for accessible focus treatment.
- `:has()` for parent-state styling where it improves the interface.
- `::backdrop` for dialogs and popovers.
- `@starting-style` for entry animations.
- `transition-behavior: allow-discrete` where discrete property transitions are appropriate.
- `:open` where supported for popover/dialog-related styling.

### CSS Anchor Positioning

Use CSS Anchor Positioning for at least one popover, tooltip, contextual menu, annotation, or callout.

- Use `anchor-name`, `position-anchor`, `position-area` or `inset-area`, and `@position-try` / `position-try-fallbacks` where supported.
- The Popover API can provide an implicit anchor relationship between a popover and its invoking control; use this where appropriate. [1][2]
- Provide a robust fallback using conventional absolute positioning, viewport-aware placement, or a non-anchored popover if anchor positioning is unavailable.
- Ensure the fallback does not clip content, obscure the trigger, or break keyboard access.

## 2.2 Motion, scroll, and visual systems

### View Transitions

Use the View Transitions API for meaningful state changes, such as:

- Route/view changes
- Opening a detail view
- Changing filters or sort order
- Switching theme variants
- Morphing a card into a detail panel

For same-document SPA transitions, wrap the DOM update in:

```js
document.startViewTransition(() => {
  // update DOM/state
});
```

Use named `view-transition-name` values for elements that should visually persist or morph between states. The View Transitions API is designed for animated transitions between DOM states in SPAs and supports customizing the transition through CSS pseudo-elements. [3][4][5]

Requirements:

- Feature-detect `document.startViewTransition`.
- If unsupported, update the DOM directly without breaking functionality.
- Respect `prefers-reduced-motion: reduce`.
- Do not use view transitions for every trivial state update.

### Scroll-driven animation

Implement at least one scroll-linked effect, such as:

- Reading-progress bar
- Sticky header state change
- Section reveal
- Parallax depth
- Animated theme-stage background
- Timeline scrubbing

Use:

```css
animation-timeline: scroll();
```

or:

```css
animation-timeline: view();
```

Gate these behind:

```css
@supports (animation-timeline: scroll()) {
  /* enhanced effect */
}
```

Provide a non-scroll-driven fallback. Never make critical content depend on scroll animation.

### Canvas, SVG, and Web Animations

Include at least two of the following:

- A procedural `<canvas>` scene, simulation, particle system, generative pattern, map, instrument display, or data visualization.
- A detailed custom inline SVG illustration, diagram, icon system, schematic, or animated motif.
- SVG filters such as turbulence, displacement, blur, lighting, or color effects where theme-appropriate.
- Web Animations API usage via `element.animate()` for interactive or state-driven motion.
- CSS keyframe animations and transitions for micro-interactions.

Requirements:

- Canvas rendering must be resolution-aware using `devicePixelRatio`.
- Use `ResizeObserver` to resize canvases correctly.
- Pause animation loops when the relevant canvas is off-screen using `IntersectionObserver`.
- Stop animation loops when appropriate, such as when the tab is hidden or the feature is inactive.
- Do not run high-CPU animations indefinitely without need.
- Respect reduced-motion preferences in both CSS and JavaScript.

## 2.3 SPA navigation and browser APIs

### Routing

Implement client-side routing with:

1. `window.navigation` / Navigation API when available.
2. A fallback using `history.pushState()`, `history.replaceState()`, and `popstate`.
3. Hash routing only if needed for maximum portability or static-file compatibility.

Requirements:

- Support back and forward navigation.
- Support direct deep links.
- Preserve scroll position where sensible.
- Update the document title for each major view.
- Handle unknown routes with a useful themed 404/not-found state.
- Avoid full-page reloads for internal navigation.
- Ensure links remain real `<a href="...">` elements where appropriate, so middle-click, new-tab, and search-engine semantics remain intact.

### Native APIs

Use several of the following where they genuinely improve the experience:

- `IntersectionObserver` for lazy rendering, active-section tracking, reveal effects, or canvas visibility.
- `ResizeObserver` for responsive canvas, layout, and component behavior.
- `AbortController` for cancellable asynchronous operations, simulated fetches, file processing, or debounceable work.
- `structuredClone()` for safe deep copies where appropriate.
- `Object.groupBy()` where grouping data improves the interface.
- `Map`, `Set`, `WeakMap`, and modern collection patterns where appropriate.
- `Intl.DateTimeFormat`, `Intl.NumberFormat`, `Intl.ListFormat`, `Intl.RelativeTimeFormat`, or `Intl.Collator` for locale-aware formatting and sorting.
- `Math.sumPrecise()` where available for precise numeric aggregation; provide a fallback reduction.
- Clipboard API for copy actions, with graceful fallback and user feedback.
- Web Share API for sharing, only when supported and contextually useful.
- BroadcastChannel for cross-tab synchronization, only if it adds real value.
- Web Audio API for optional, user-initiated, muted-by-default sound.
- File System Access API only as an optional enhancement, never as a requirement.
- `picture-in-picture`, fullscreen, vibration, geolocation, notifications, or other permission-based APIs only if essential to the theme and always with explicit user consent.

Do not add APIs merely to name-drop them. Each selected API must solve a real UX or engineering problem.

# 3. RESPONSIVENESS, PERFORMANCE, AND ACCESSIBILITY

## 3.1 Responsive experience

- Begin with a 320 px mobile layout.
- Scale gracefully through phone, tablet, laptop, desktop, and ultra-wide sizes.
- Use touch targets of at least 44 × 44 CSS pixels where practical.
- Ensure horizontal scrolling is not required except inside explicitly scrollable data tables, code panels, timelines, or media galleries.
- Provide visible scroll affordances when content overflows.
- Test keyboard-only use on every primary flow.
- Ensure the layout works in both portrait and landscape orientations.

## 3.2 Accessibility

Meet WCAG 2.2 AA or better for the primary experience.

Required practices:

- Use semantic landmarks: `<header>`, `<nav>`, `<main>`, `<section>`, `<article>`, `<aside>`, and `<footer>`.
- Maintain a logical heading hierarchy.
- Include a skip-to-content link.
- Ensure all interactive controls are reachable and operable by keyboard.
- Provide clear, visible focus indicators.
- Use native elements first; add ARIA only when native semantics are insufficient.
- Use `aria-live="polite"` for non-urgent status updates, such as filter results, save confirmations, simulation readouts, or copy success.
- Use `aria-live="assertive"` sparingly, only for urgent errors.
- Ensure dialogs trap or manage focus appropriately and close with `Escape`.
- Ensure popovers support light dismiss and keyboard dismissal where native behavior provides it.
- Maintain sufficient color contrast for text, icons, controls, and meaningful graphical elements.
- Do not rely on color alone to convey status.
- Provide text alternatives for informative SVGs and canvas visuals.
- Mark purely decorative SVGs and canvas elements appropriately with `aria-hidden="true"` and/or `role="presentation"` where suitable.
- Honor `prefers-reduced-motion: reduce` and `prefers-contrast: more` where relevant.
- Ensure form errors are associated with inputs through `aria-describedby`, `aria-invalid`, and visible error text.

## 3.3 Performance

- Avoid layout thrashing and unnecessary reflows.
- Batch DOM updates where practical.
- Use event delegation for large lists.
- Debounce or throttle high-frequency events such as resize, scroll, input, pointer movement, and canvas interaction.
- Use `requestAnimationFrame()` for visual loops.
- Cancel stale async work with `AbortController`.
- Lazy-render long lists using windowing, pagination, progressive reveal, or virtualization only if needed.
- Keep the initial payload small.
- Avoid memory leaks by removing listeners, canceling animations, revoking object URLs, and disconnecting observers when appropriate.
